For these << Edge cases and strange cases — types
Codes versus labels. The code is the stable, machine-meaningful part; the label is what humans read. Renaming a label is safe at any time and changes every dropdown instantly. Changing a code is not a rename, it is a behavioural edit: code is how other layers recognise a kind, so codes are treated as immutable once a type has been used, and retired-and-recreated is the path instead.

A type in use cannot vanish. A type referenced by a live property, pricing or policy value is retired rather than deleted: the row stops appearing in selection lists, existing references keep resolving, history keeps meaning what it meant. The lookup surface's delete method exists for admin use, but the service behind it must answer the "is anything pointing at this" question first — a catalogue delete that orphans a property's type reference is a corrupt property, and the plan refuses it.

Hierarchy edits. Reparenting a type moves a subtree; creating a cycle (type A under B under A) would make the catalogue unresolvable, so any reparent that would place a node beneath its own descendant is refused. Retiring a parent does not cascade-retire its children — children keep their own status, and a retired parent simply disappears from root-level selection while its subtree stays reachable through its children's own entries.

Concurrency. Two admins editing the same type concurrently: last write wins at the field level, but because every write is versioned through the logs table with before and after data, neither edit is lost to history — the operator can always reconstitute what each admin saw and when.

Empty and whitespace codes, duplicate labels. A blank code is never valid. Two types under the same entity may share a label (a "Standard" room kind and a "Standard" pricing cadence are different rows under different entities); two types under the same entity with the same code are the same type and are refused as duplicates.

View tiers seeing retired types. Read methods return the full catalogue including retired rows when asked by id — history and existing selections must resolve — but list methods used for selection UIs filter to active rows, so a personal user's dropdown never offers a retired kind.

The type of a type. The hierarchy itself is not typed: parent links always mean "kind of", never anything else, and the entity binding of a child must equal the entity binding of its parent — a property kind cannot hang beneath a visit format, because the entity is the namespace and the hierarchy stays inside it.>> typew wilmoves forlooupd surfacean beome an fullfledgedd module with controller
